Implementation plan · 14 September 2026

Klårt Build Plan

How to implement the five features the market analysis rated High or Very High, in the order that gets a validation cohort started soonest: open any markdown folder, an Apple on-device provider, Discuss with a writer profile, the whole-document read, and rubric packs. Team rubrics are designed for, not built.

Summary

Build in the order the validation cohort needs it: remove the two reasons not to start (a note silo, a model to install), then add the one thing that makes people come back (an editor that argues and remembers), then widen what it reads (the whole document) and what it reads for (rubrics). About 40 developer-days, in five shippable increments, none of which throws away existing code.

  1. Folder library first. Abstract NoteStore behind a NoteStoring protocol and add a FolderNoteStore that reads and writes plain .md files in a user-chosen folder, with a .klart/ sidecar for identity and verdicts. Vault encryption stays a managed-library feature. 7–9 days.
  2. Apple provider second. A ProviderKind.apple backed by the Foundation Models framework behind canImport and availability checks, with guided generation instead of JSON parsing and a compact prompt profile for the 4,096-token window. Zero setup, zero cost, weak model: position it as the starter. 4–6 days.
  3. Discuss and the writer profile third. Threads stored in a sealed discussions.json, a discussion prompt that must end [withdrawn] or [stands], a card that expands in place, and a deterministic profile rendered into a new optional {{WRITER_PROFILE}} token. This is the retention feature and the A/B test in the 90-day plan. 11–14 days.
  4. Whole-document read fourth. A second read mode with its own template and a document skeleton (outline plus first and last paragraph per section), notes tagged with a scope so the rail can pin them under the title, and three new offline checks. Designed with a {{DOCUMENT_RUBRIC}} token that rubric packs fill later. 5–7 days.
  5. Rubric packs fifth. A JSON rubric format that reconfigures the nine lenses, adds section and document rules, and ships six built-in packs; per-note selection; import and export; a .klart/rubrics/ folder in folder libraries so teams can share via git. Custom lenses deferred. 6–8 days.
  6. Team rubrics are a set of constraints on the above, not a build item: rubrics never carry endpoints, managed rubrics are read-only, and the profile can be exported without content. Honouring them now costs nothing and keeps alternative 2 open.
Principles

Rules every increment follows

Lenient decoding, always

Every new field on Note, AppSettings, FeedbackItem and RecommendationRecord decodes with a default, exactly as the existing custom init(from:) implementations do. A settings file from any build opens in any other build.

The vault covers every new file

DiscussionLog and the profile store mirror RecommendationLog: setEncryptionKey, lock, encryptOnDisk, decryptOnDisk, rotateOnDisk, and calls from enableProtection, disableProtection, resolveMasterKey and rotateMasterKey in AppState. Each gets its own AAD string.

Sensitive stays sensitive

The request-time rule in AppState.sensitiveNoteBlocked applies to Discuss, the document read and the Apple provider alike. Private Cloud Compute counts as cloud for this rule, whatever Apple's privacy claims: the promise to the user is literal.

Pure logic in KlartKit, tested there

Prompt building, parsing, skeletons, the profile derivation and the rubric format are pure functions in KlartKit with XCTest coverage. The app layer only orchestrates. The sample note in SampleNote.swift gains cases that trip each new feature.

No telemetry, still measurable

The 90-day plan needs numbers. They come from the learning log and the new discussion log, exported by the user. The profile A/B is a local setting, not a remote flag.

One release per feature

Each section below ends in a definition of done, a version bump in project.yml and a PRD update. Nothing waits on the next feature to ship.

Now Feature 1 · Very high impact · 7–9 days

Open any folder of markdown

Klårt keeps every note as a JSON file under a UUID in Application Support and only round-trips markdown through export and import1. The change: a second library type where the notes are the user's own .md files in a folder they pick, edited in place, with Klårt's metadata in a sidecar. Obsidian vaults, iA Writer libraries and git repositories become usable without migration.

Design decisions

Identity
A folder note's identity is its path relative to the library root. A stable UUID is minted on first sight and kept in the sidecar, so RecommendationRecord.noteID, rejected fingerprints and the coming discussion threads keep working unchanged. A rename outside Klårt looks like delete plus create; the sidecar entry is reattached when a file with the same content hash reappears within the same scan, otherwise it is orphaned and pruned after 30 days.
Sidecar, not front matter
<root>/.klart/meta.json maps relative path to { id, rejectedFingerprints, isSensitive, rubricID, lastSeenModified, contentHash }. The user's files are never rewritten with Klårt data. Front matter can be offered later as an opt-in for Obsidian users; it is not needed for v1. .klart/ is documented as safe to git-ignore or to commit.
File format
UTF-8 markdown, exactly what the editor holds. Writes go to a temporary file in the same directory followed by replaceItemAt, preserving the original's attributes. Line endings are preserved as read (CRLF files stay CRLF). Note.title(of:) falls back to the filename without extension when the file has no heading or first line.
Scope of a scan
Recursive, .md and .markdown only, skipping any directory that starts with a dot (.obsidian, .git, .klart) and node_modules. Symlinks are not followed. A scan of 2,000 files should stay under one second; contents are loaded eagerly in v1 because AppState.notes holds full notes, and a lazy-content variant is listed as a follow-up if the cohort brings larger vaults.
External edits
A DispatchSource on the root directory plus a rescan on NSApplication.didBecomeActiveNotification. For the selected note: if the file's modification date moved and the editor buffer is unchanged since load, reload silently; if both changed, keep the buffer, write nothing, and show a one-line conflict notice in the rail with "Reload from disk" and "Keep mine". Autosave never overwrites a file whose modification date is newer than the one last read.
Sandbox
The existing com.apple.security.files.user-selected.read-write entitlement covers a folder chosen in an open panel and all its descendants1. Persist a security-scoped bookmark (URL.bookmarkData(options: .withSecurityScope)) in settings and call startAccessingSecurityScopedResource at library open. A stale bookmark falls back to the managed library with a notice rather than an empty screen.
Encryption
The vault seals the managed library only. Opening a folder while the vault is on is allowed; Settings → Security states plainly that folder libraries are plain files. App lock, auto-lock and capture exclusion still apply to the window. Sensitive marking works in folder mode through the sidecar.
One library at a time
Settings gain a library: LibraryLocation with cases managed and folder(bookmark: Data, displayName: String), plus a recent-folders list of five. Switching flushes the editor, tears down the store and reloads. The managed library remains the default for new installs; the welcome tour gains one screen offering "Open a folder you already write in".

Now Feature 2 · High impact · 4–6 days, plus 2 for macOS 27

Apple Foundation Models provider

Today the quick start says "install Ollama and pull llama3.2". On macOS 26 an Apple-silicon Mac with Apple Intelligence carries a free on-device model behind the Foundation Models framework, with guided generation and a 4,096-token context3,4. Klårt should read with it out of the box and treat Ollama, LM Studio and OpenRouter as upgrades.

Design decisions

Compile and run guards
The deployment target stays macOS 14. The client lives in #if canImport(FoundationModels) and every call site checks if #available(macOS 26, *). SystemLanguageModel.default.availability decides whether the provider is listed: unavailable reasons (device not eligible, Apple Intelligence off, model downloading) are shown verbatim in Settings and in the welcome tour3. On macOS 14 and 15 the provider does not appear at all.
A structured path beside the text path
Add protocol StructuredFeedbackClient: LLMClient { func feedback(system: String, user: String, kinds: [FeedbackKind], maxItems: Int) async throws -> [FeedbackItem] }. The Apple client implements it with a @Generable round type whose type is constrained to the enabled kinds and severity to 1...3, so the parser's salvage logic is never needed. FeedbackEngine.analyze prefers the structured path when the client offers it and falls back to complete plus FeedbackParser otherwise. Anchor verification and rejected-fingerprint filtering stay exactly where they are.
Compact prompt profile
The current budgets (8,000 characters of section, 16,000 of document) exceed a 4,096-token window on their own. Introduce PromptBudget with two presets: standard (today's numbers) and compact (section 2,500 characters, document context replaced by the outline plus the first sentence of each section, capped at 800 characters, maxTips forced to 3, detail brief). LLMClient gains var promptBudget: PromptBudget { get } with a default of standard. A context overflow error from the framework is caught and retried once at half the section budget before surfacing.
Streaming for coach actions
stream wraps session.streamResponse(to:), which yields cumulative snapshots; the client emits the delta between snapshots so the existing coach popover code is untouched.
Locality
ProviderFactory.isLocal returns true for the on-device model: sensitive notes may use it. When the macOS 27 Private Cloud Compute variant is adopted, it is a separate ProviderKind.applePrivateCloud that reports non-local, so sensitive notes refuse it under the existing rule4.
Default selection
On first launch, if the Apple model is available the active provider is set to .apple; otherwise .ollama as today. The welcome tour's provider page says which happened. Settings keep the full picker.
Quality framing
A 3B model will miss warrants and counters a frontier model catches. The provider's Settings row carries one line: "Good for offline and quick reads; for a demanding editor, connect a larger model." The Nordbrot sample becomes the acceptance test: the on-device read must surface at least the uncited claim, the hedging and one overlap.
macOS 27
When the macOS 27 SDK is in use, adopt the LanguageModel protocol so the Apple, Anthropic and Google packages plug into the same client, and add the Private Cloud Compute model with the standard prompt budget. Eligibility for Apple's free cloud tier is tied to the App Store Small Business Program and needs the App Store build, so a KLART_DISTRIBUTION compile flag distinguishes the App Store and direct builds4. These API names come from session summaries and must be checked against the SDK headers before implementation.

Now Feature 3 · Very high impact · 11–14 days

Discuss, and the writer profile

PRD §3.6 already specifies the interaction and the storage1. This section turns it into a build order, fills in the pieces the PRD leaves open (how preferences are captured deterministically, how the profile enters the prompt, how the A/B test works), and splits the work so a usable Discuss ships before the profile.

3a · Thread model and storage (2 days)

Model
DiscussionThread { id: UUID, noteID: UUID?, fingerprint: String, kind: FeedbackKind, sectionTitle: String?, turns: [Turn], outcome: DiscussionOutcome, createdAt, updatedAt, fromSensitiveNote: Bool } with Turn { role: .writer | .editor, text: String, at: Date, rememberAsPreference: Bool } and DiscussionOutcome { open, withdrawn, stands, abandoned }. For a sensitive note the turns are stored with empty text and only the signal survives, matching the learning log's two tiers.
Store
DiscussionLog actor, one sealed file discussions.json beside recommendations.json, AAD klart.discussions, the same key lifecycle. AppState vault methods call it alongside the recommendation log. Threads are keyed by note id plus fingerprint so re-opening Discuss on the same note resumes the thread.
Log linkage
RecommendationRecord gains reason: String? (values argued, conceded) and threadID: UUID?, both lenient. Export schema becomes klart.recommendations.v3; the v2 reader still loads.

3b · Prompting and parsing (2 days)

Template
PromptBuilder.defaultDiscussionTemplate: the editor defends the note against the section, concedes when the writer is right and says so plainly, never drafts, and ends every turn with exactly one marker, [withdrawn] when the note was wrong, [stands] when it holds, or nothing while the point is still open. Tokens: {{DISCUSSION}} (the instruction), {{STYLE}}, {{WRITER_PROFILE}}. Stored override in AppSettings.discussionSystemPrompt, editable in Settings → Editor with the same legend and missing-token warning.
Messages
discussionMessages(context:item:thread:style:template:) sends the system prompt, the anchored section in full, the note (kind, anchor, text, why), and the thread so far as alternating user and assistant messages. Budget: the section clipped to sectionBudget, the thread to its last twelve turns.
Parsing
DiscussionReply.parse(_:) -> (text: String, verdict: DiscussionOutcome?) strips a trailing marker case-insensitively and tolerates it inside a code span or on its own line. A reply with two markers counts as none.

3c · The card that argues (4 days)

Teleprompter
Third quiet action on every card, Discuss, beside Respond. The card expands in place into a thread: note at the top, the writer's turns right-aligned in secondary ink, the editor's turns streaming into the card under the reading pulse, a reply field at the foot (⌘↩ sends, Esc folds). While a thread is open the rail widens to railMaxWidth and the layout pass in EditorBridge treats the open card's measured height as its anchor extent so cards below step down rather than overlap. Folded, the card carries a count, 3 ↩.
Classic
The same thread as a sheet from the popover row, reusing the thread view.
Outcomes
[withdrawn] records rejected with reason argued, adds the fingerprint to the note's rejected list, and fades the card as a rejection does today. [stands] records confirmed with reason conceded only if the writer then presses Respond or Confirm; otherwise the thread stays open and is marked abandoned when the note is replaced by a later read, which logs dismissed as now.
Respond from a thread
NoteEditing.respond(to:conclusion:in:cursorUTF16:) quotes the editor's last turn instead of the original observation. The block keeps the kind and anchor so the writer sees which note it came from.
State
AppState: openThread: DiscussionThread?, discussionTask, sendTurn(_:for:), foldThread(). A keystroke in the editor does not cancel a running discussion turn; a new read of the same section does.

3d · Writer profile (3 days)

Derivation
WriterProfile.derive(records:threads:now:) -> WriterProfile is pure, deterministic and model-free. It computes acceptance per kind (responded plus confirmed over all judged, kinds with fewer than five verdicts omitted), the writer's standing preferences, and the three most recent conceded points as kind, section title and date. render() produces at most 600 characters in a fixed order so the same inputs always give the same prompt bytes and the prompt hash stays stable between verdicts.
Preferences without NLP
The PRD's "stated standing preferences" are captured explicitly: a writer turn has a small "remember this" toggle. Only toggled turns enter the profile, verbatim, capped at five and at 120 characters each, newest first. Nothing is inferred from free text, so the profile never surprises the writer with a preference they did not set.
Prompt entry
The default feedback template gains, after the rules, the block: What you know about this writer (may be empty):\n{{WRITER_PROFILE}}. The token is optional; a custom template without it simply gets no profile. Rendering it changes systemPromptHash for every user of the default, which is what the hash is for; the log shows the version boundary.
Storage and control
profile.json, sealed under the vault with AAD klart.profile, regenerated after every verdict and thread outcome. Settings → Editor: view the rendered profile, export it, clear it, and a toggle useWriterProfile (default on).
Recall in notes
The template asks the editor, when a profile point matches the current note, to name it in why ("you conceded this in Pricing on 12 Aug"). This costs no new fields.

3e · Measurement for the cohort (1 day)

A/B
The cohort is split by hand: half are asked to leave useWriterProfile off for weeks 7 to 10. Each exported log carries the setting's value at verdict time (new signal-tier field profileUsed: Bool), so acceptance rates can be compared per arm without any server.
Progress view (optional, 1 day)
The same derivation renders a Settings → Editor panel: acceptance per kind over the last 30 and 90 days, threads opened, points conceded. It is the visible form of the coaching claim and costs almost nothing once WriterProfile.derive exists.

Tests

  • DiscussionLogTests: append, resume by note and fingerprint, vault enable, disable and rotate, sensitive stripping.
  • DiscussionReplyTests: markers at end, on their own line, in a code span, doubled, absent.
  • WriterProfileTests: determinism, the 600-character cap, the five-verdict threshold, ordering of conceded points, preference cap and truncation, empty inputs render an empty string.
  • PromptAndEngineTests: the discussion messages carry the thread in order and clip it; the feedback prompt with an empty profile equals today's prompt byte for byte except the new block.
  • KlartAppTests: an open thread widens the rail and steps the cards below it; Esc folds and restores; a read of another section does not cancel a running turn.

Definition of done

  • A writer can argue a note to a withdrawal and see it recorded as rejected with reason argued.
  • After twenty verdicts the profile appears in the prompt and Settings shows the same text.
  • Turning the profile off restores the exact previous prompt.
  • Threads and profile are sealed, rotated and cleared with the rest of the library.
Now Feature 4 · High impact · 5–7 days

Whole-document read

Every read today is about one finished section against the document. The failures partners and supervisors care about most are document-level: an opening that does not state the answer, an order that is bottom-up, a section that does not earn its place, a conclusion that promises more than the body delivered. This adds a second read mode with its own trigger, prompt, skeleton and card treatment.

Design decisions

Trigger
On demand only in v1: Editor ▸ Read the Whole Document (⌘⇧R), the typed command //document, and a "Read everything" action in the rail's empty card once at least three sections have been read. An automatic trigger (all sections read and five minutes idle) is a setting, off by default, added after the cohort says whether it wants it.
What the model sees
PromptContext.skeleton(text:budget:) builds, in order: the H1, the outline with levels, the opening section in full, and for every other non-excluded section its first and last paragraph, clipped so the whole fits the client's PromptBudget.documentBudget. Clients with the standard budget get the full redacted document when it fits and the skeleton when it does not. The compact budget always gets the skeleton.
Template
PromptBuilder.defaultDocumentTemplate: the same voice, the same JSON shape, but every item names the section it is about in a required section field, which must be a heading from the outline; items about the document as a whole use the H1. Rules: does the opening state the conclusion the body supports; is each top-level section a reason for it; which section does not bear on the claim; does the close deliver what the opening promised; do the top-level sections overlap or leave a gap. A {{DOCUMENT_RUBRIC}} token, empty by default, is where rubric packs (feature 5) insert genre rules. Override stored in AppSettings.documentSystemPrompt.
Scope on items
FeedbackItem gains scope: FeedbackScope with cases section and document, lenient default section. The fingerprint includes the scope so a document note and a section note on the same words are different identities. The engine verifies the named section against the outline (case and whitespace folded); a miss falls back to the H1 rather than dropping the note, because a document-level observation without a section is still useful.
Replacement rule
replaceNotes(for:with:) is extended: a document read replaces only document-scope notes; a section read replaces only section-scope notes for that section. Verdict carry-over by fingerprint is unchanged.
Rail treatment
Document notes render as a group pinned under the title band, above the first section's cards, with a small ¶ beside the kind glyph. In the classic layout they lead the list under a "Whole document" header. Respond on a document note inserts the block at the end of the named section, or directly under the H1 for H1-scoped notes.
Offline checks
Three new document-scope rules in LocalChecks, run on every document read and, cheaply, on every section read so they appear before any model: heading-depth-jump (H1 to H3 with no H2, kind structure), no-conclusion (no heading matching a small per-language list such as conclusion, recommendation, summary, so what, Fazit, Empfehlung, conclusión, in a document with three or more sections, kind gap), and question-title-unanswered (an H1 ending in a question mark with no section whose first paragraph contains a claim word from the language list, kind warrant). Each is one function with a table-driven test.
Cost control
A document read is the most expensive call the app makes. It is never automatic in v1, it is skipped when the document is under three sections, and it reuses the last skeleton when the text has not changed since the previous document read.

Next Feature 5 · High impact · 6–8 days

Rubric packs

The nine lenses are one rubric, the general one. A consulting memo, a thesis chapter, a grant proposal and a product requirements document each fail a demanding reader in their own ways. A rubric pack is a file that retunes the lenses, adds section and document rules and offline checks, and can be shared. Custom lenses with their own glyphs are deliberately out of v1: the monochrome glyph system and FeedbackKind stay closed.

Format

{
  "schema": "klart.rubric.v1",
  "id": "consulting-memo",
  "name": "Consulting memo",
  "description": "SCQA opening, answer first, MECE reasons, every number sourced.",
  "languages": ["en", "de"],
  "lenses": {
    "gap":      { "enabled": true,  "instruction": "A consideration a partner would raise that the memo does not address." },
    "evidence": { "enabled": true,  "instruction": "A number or fact with no source, or a source that does not say this." },
    "warrant":  { "enabled": true },
    "clarity":  { "enabled": false }
  },
  "sectionRules": [
    "The first sentence of a section is its conclusion; flag a section that opens with background.",
    "Any recommendation without a named owner, cost or date is incomplete."
  ],
  "documentRules": [
    "The opening must state the situation, the complication, and the answer within the first 120 words.",
    "Every top-level section must be a reason for the answer, not a chapter of background."
  ],
  "localChecks": {
    "hedgeWords": ["might", "could", "perhaps", "möglicherweise"],
    "requiredSections": ["Recommendation", "Empfehlung"],
    "maxSectionWords": 400
  },
  "defaults": { "tone": "direct", "detail": "standard", "maxTips": 3 },
  "managedBy": null
}

Design decisions

Where rubrics live
Built-in packs are resources in KlartKit: general (today's behaviour, byte-identical prompt), consulting memo, thesis chapter, grant proposal, product requirements or RFC, policy brief. User packs live in Application Support/Klart/Rubrics/. In a folder library, .klart/rubrics/ is read as well, so a team can commit a rubric to its repository and everyone who opens the folder sees it. Precedence on id collision: library folder, then user folder, then built-in.
Selection
AppSettings.defaultRubricID (default general) and Note.rubricID per note, stored in the note JSON or the sidecar. The Teleprompter shows the rubric name in secondary ink beside the pinned title; clicking opens a small picker. The classic toolbar gets the same picker.
Prompt integration
PromptBuilder.feedbackMessages and documentMessages take a Rubric. Lens instructions from the rubric replace FeedbackKind.instruction for enabled kinds; sectionRules join the rules list before {{STYLE}}; documentRules fill {{DOCUMENT_RUBRIC}}. A user-edited template keeps working because the rubric content enters through the existing tokens plus one new optional {{RUBRIC_RULES}}. The rubric id and a hash of its content join the signal tier of the learning log so acceptance rates can be read per rubric.
Offline checks
LocalChecks.run takes a RubricChecks value: the hedge-word list replaces the built-in one when present, requiredSections produces a missing-section gap note at document scope, maxSectionWords produces a long-section structure note. Rule names stay learnable in the card.
Import and export
File ▸ Import Rubric… copies a validated file into the user folder; a malformed file reports the first schema error and is not copied. Export writes the active rubric, including a built-in one, so a user can start from it. Rubrics never contain endpoints, keys or model names (see feature 6); the validator rejects unknown top-level keys.
Validation
Rubric.validate checks the schema string, that every lens key is a known kind, that instructions are under 300 characters, that rules number at most ten each, and that the file is under 32 KB. Errors are user-readable and tested.

Later Feature 6 · High impact for B2B · constraints only

Team rubrics and supervisor mode: what to protect now

Not built in this plan. Alternative 2 in the market analysis (a review desk for advisory firms) depends on it, and four small constraints keep the path open at no cost2.

Rubrics carry no configuration of where text goes

No endpoint, key, model or provider fields, ever. A rubric is a set of standards, not a route. Anything that decides where notes are sent lives in settings, and for managed fleets in managed preferences under the bundle id, which the app reads before its own settings file.

A managed rubric is read-only

The managedBy field, when set, marks a rubric the app will not let the user edit in place; they can duplicate it. This is enough for a firm to publish standards through a shared folder.

The profile exports without content

The writer profile and the progress view derive from the signal tier alone when content logging is off. A supervisor report is therefore a content-free export the writer chooses to share, never something the app sends.

Verdicts are attributable to rubric and prompt

With rubric id and hash in the log (feature 5), a firm can compare acceptance across its own rubric versions. This is the data a quality lead would buy, and it is already being collected locally.
